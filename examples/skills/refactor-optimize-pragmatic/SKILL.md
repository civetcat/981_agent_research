# 務實重構與優化

## 目標

在**已改動或即將收斂的程式碼**上，重新審視並做必要優化，且同時滿足：

1. **不要過度設計**：只解決真問題；能三行說清楚的不要三層抽象。
2. **功能需要正常**：行為與邊界條件與原本意圖一致；改壞比不改更糟。
3. **可讀性**：命名與結構讓下一個讀的人（含未來的自己）能快速理解意圖與資料流。

## 建議流程

1. **釐清範圍**：本次變更要達成的行為是什麼？哪些檔案/函式在 diff 內？
2. **先找既有實作**：專案內是否已有相同模式的 helper、錯誤處理、重試、驗證函式；**優先沿用**，避免平行實作。
3. **小步修改**：每次改動最好對應一個清楚意圖（例如「合併重複錯誤處理」）；避免同一輪混雜無關重構。
4. **對照行為**：列出會受影響的輸入/錯誤路徑/併發情境；改完在心裡或註解旁快速走一遍。
5. **能驗證就驗證**：有測試則跑相關測試；無測試則至少確認編譯與關鍵手動路徑（依專案習慣）。

## 約束細則

### 1. 避免過度設計（紅線）

- 不為「可能將來會用到」而引入介面層、plugin 架構、通用框架。
- 不重寫整個模組，除非使用者明確要求或現況已無法安全修改。
- 不新增與任務無關的設定檔、大量註解長文、或「教學用」範例程式。
- **預設**：刪減多餘分支與重複，比新增抽象層更值得做。

### 2. 正確性優先

- 不為效能微優化而犧牲錯誤處理、取消/逾時、資源釋放。
- 改簽名或資料結構前，確認呼叫端與序列化/持久化是否一併更新。
- 若無法確定行為是否改變：**寧可少改**，或先加最小測試/斷言再動邏輯。

### 3. 可讀性

- 命名以「意圖」為主；變數生命週期短則可接受較短名，但 public API 要清楚。
- 優先讓控制流線性可讀（early return、小函式），而不是聰明的單行技巧。
- 重複出現三次以上的邏輯，才考慮抽出；抽出後呼叫點應變短、變清楚。

## 優化時可問自己的問題

- 這段程式**最難維護的點**是什麼？是否用**最小改動**就能緩解？
- 若刪掉這個抽象/層級，行為是否仍清楚？若答案是「是」，考慮刪除。
- 新讀者從呼叫端往內追，會不會在第三個檔案迷路？若會，是否只需搬近一點或改名？

## 與「純 Review」的差異

- 本 skill 預設會**實際改程式**（在使用者要求實作的前提下），但以**小 diff、可合併、可解釋**為原則。
- 若僅要意見不要改檔，改以條列建議輸出即可（由使用者指令決定）。

## 輸出建議（改完程式時）

簡短說明即可（繁體中文）：

- **做了什麼**：1–3 點
- **為什麼**：對應「不過度設計 / 正確性 / 可讀性」哪一項
- **風險/驗證**：若有行為敏感處，寫如何確認
