# Karpathy Coding Principles

## 目標

在非 trivial 的開發工作中，降低以下風險：

- 沒確認假設就一路做下去
- 把簡單問題做得過度複雜
- 順手改到與需求無關的地方
- 沒有明確驗證就宣稱完成

## 什麼時候用

特別適合這些情境：

- 修 bug，但需求或根因還不夠清楚
- 在既有程式碼上做功能修改
- 重構、最佳化、清理實作
- 任務看起來不大，但其實容易誤判範圍
- 使用者只說「幫我改」，但成功條件不夠明確

如果只是明顯的一行小修、純文案修改、或不需要推理的機械性變更，可只套用其中的「最小修改」原則。

## 核心原則

### 1. 先想清楚再動手

- 不要默默選一種解讀就開始做。
- 先確認：需求是什麼、邊界在哪裡、成功條件是什麼。
- 若有歧義，先提出 1 到 2 個合理解讀，必要時先問使用者。
- 若看到更簡單的做法，應主動指出，而不是直接堆設計。

### 2. 簡單優先

- 用最少的程式碼解決眼前問題。
- 不為了「以後可能用到」加入抽象層、設定項、擴充點。
- 不新增未被要求的功能、錯誤處理分支、或通用框架。
- 若 50 行能解決，就不要寫成 200 行。

### 3. 外科手術式修改

- 只改與目前需求直接相關的程式。
- 不順手重排附近程式、重寫註解、或做無關重構。
- 優先沿用專案現有 helper、模式與函式，避免平行實作。
- 如果你發現無關的壞味道，可以提一下，但不要順便大改。

### 4. 目標導向驗證

- 每個任務都要能回答「怎樣算完成」。
- 能寫測試就寫最小必要測試；不適合寫測試時，至少做明確驗證。
- 修 bug 時，優先先建立可重現方式，再修正並確認不再重現。
- 重構時，確認行為不變，而不是只看程式變漂亮。

## 預設工作流程

1. 先用 1 到 3 句話重述需求與假設。
2. 找現有實作、既有 helper、相似模式，優先重用。
3. 選最直接的方案，避免過度設計。
4. 小步修改，只碰必要檔案與必要邏輯。
5. 用測試、編譯、或最小手動驗證確認結果。
6. 回報時簡短說明：改了什麼、怎麼驗證、剩下什麼風險。

## 實作時的自我檢查

開始前先問自己：

- 我是不是在假設某件事成立？這件事有被證實嗎？
- 專案裡是不是已經有類似做法？
- 我現在加的抽象，真的是現在需要的嗎？
- 這個改動有沒有碰到與需求無關的程式？
- 我有沒有一個明確方式證明這次修改是對的？

## 遇到這些情況要停一下

- 需求有兩種以上合理解釋，而且會導致不同實作
- 你找不到根因，只是在猜
- 你需要大範圍重構才能繼續，但使用者沒有要求
- 你正準備新增通用框架來解一個單點問題

此時應先說明觀察到的分歧或風險，再決定是否繼續。

## 輸出偏好

回覆應偏向：

- 短、直接、可驗證
- 先講風險與假設，再講做法
- 若有 trade-off，明確說出較簡單方案為何
- 完成後只總結與本次需求直接相關的修改

## 一句話版本

先確認假設，再用最小改動解決真正問題，並用明確方式驗證完成。
