韌體更新

韌體更新是透過將 .upd 檔案放在點讀筆上來進行。點讀筆上有一個名為 LanguageInfo.txt（或 LanguageInfoMT.txt 或 LanguageInfo5E.txt... 視執行中的韌體而定）的檔案，該檔案用來定義點讀筆正在尋找的更新檔案名稱。該檔案包含如下清單：

3<0x0d><0x0a>
999 GERMAN Update3202.upd<0x0d><0x0a>
998 FRENCH Update3202_fr.upd<0x0d><0x0a>
997 DUTCH Update3202_nl.upd<0x0d><0x0a>

第一欄表示語言 OID 碼（這是用來初始化新點讀筆使用特定語言的 OID。每支新點讀筆都附帶一張啟動紙，上面印有包含該 OID 的欄位，點讀筆需讀取（一次）該欄位），第二欄是點讀筆在 GME 檔案中尋找以匹配點讀筆語言的單字。第三欄則顯然是該語言對應的更新檔案名稱。

某些語言有（額外）命名不同的更新檔案。在本專案的 scripts 目錄中，您會找到一些腳本負責下載大多數韌體。

.tiptoi.log

點讀筆上有一個隱藏檔案，表示記憶棒的語言。以下是該檔案的內容：

00000000  41 42 31 32 33 34 35 36  ff ff ff ff ff ff ff ff  |AB123456........|
00000010  4e 30 30 33 38 00 00 00  00 00 ff ff ff ff ff ff  |N0038...........|
00000020  47 45 52 4d 41 4e 00 00  00 00 ff ff ff ff ff ff  |GERMAN..........|
00000030  33 32 30 32 4e 00 00 00  00 00 ff ff ff ff ff ff  |3202N...........|

此檔案由四個「行」組成：

  • 點讀筆的序列號（在此範例中已替換為 AB123456）。
  • 韌體版本（可在韌體更新檔案中找到的字串）。每次點讀筆開機時都會更新。
  • 點讀筆韌體的語言
  • 處理器名稱

如果您移除 .tiptoi.log 檔案，點讀筆必須使用啟動紙重新啟動。

韌體版本字串

韌體版本字串似乎最多由 10 個字元組成。目前韌體有五或七個字元的版本。皆以一個字母加上四位數字開始，其中有些在數字後附加 'MT'。基於 ZC3202N 裝置的韌體顯示這些版本（最後檢查：2015-02-06）
* 德國: "N0038" (20120419)
* 法國: "f0021" (20131120) 或 "f0023MT" (20131120)
* 荷蘭: "h0013" (20130117) 或 "h0013MT" (20131003)
* 義大利: "i0010" (20140213) 或 "i0012MT" (20131203)
* 俄羅斯: "r0007MT" (20140912)

顯然第一個字元對應語言，除德國韌體外（也許原因是德國是第一個市場，他們在德國市場推出後才加入該命名方案）。德國韌體中的 'N' 可能指 Chomptech 處理器名為 ZC3202N。

基於 ZC3201 的裝置，目前韌體為 v136 (最後檢查 2018-11-13)。

基於 ZC3203L 的裝置，目前韌體為 "2G0042 (適用於德國)。

您可以使用十六進位編輯器或 Linux 上的 "strings" 工具查看 upd 檔案末尾來檢查版本。有一個看起來像 "ANYKA_IDRAV2G0042" 的字串。"RAV" 後的右側部分是韌體版本。"RAV" 可能代表 "Ravensburger"。

如何切換點讀筆的語言

  • 在 LanguageInfo.txt 中，將所需語言第一欄的數字與目前語言的數字交換（見上文）。如果檔案遺失，您可以自行建立一個，見上文格式
  • 將新語言的更新檔案放在點讀筆上（正確檔案名稱可在 LanguageInfo.txt 中找到）
  • 開機點讀筆。它會（以新語言）告訴您正在更新，然後重新開機

自 2021 年起，Ravensburger 部分支援語言切換（透過 Tiptoi Manager）官方支援：https://service.ravensburger.de/tiptoi/Fragen_zum_tiptoi_Stift/Spracheinstellungen_des_tiptoi_Stiftes (德文)

模式

點讀筆可運行多種模式：
* 正常操作模式
* 測試模式 (執行某些測試)

測試模式

按住音量減按鈕同時按下開機按鈕進入此模式（對於新 Player 點讀筆，您可能想按住倒退按鈕同時按下開機按鈕）。點讀筆不得透過 USB 連接！

進入該模式時，您會先聽到（中文）"Testmode" ("Toshe mo she")、"Start test of program" ("Cashe toshe ton tjio")，接著是 "Program test pass" ("ton tjio toshe dchin tao") 或 "Program test fail" ("ton tjio toshe she by")。現在您可以按 "+" 運行某些測試。每按一次會啟動下一個測試（依此順序描述）：
* "Start test of the tip of the pen" ("cashe toshe beat ho") 接著是 "Test of the tip of the pen passed" ("beat ho toshe dchin tao") 或 "Communication to the tip of the pen failed" ("beat ho toshe she by")
* "Start test of encryption procedure" ("cashe toshe dja mee")，之後需一段時間無法操作，然後您會聽到 "Encryption procedure test passed" ("dja mee toshe dchang gung") 或 "Encryption procedure test failed" ("dja mee toshe she by")。這可能使用點讀筆上的 TestFile 目錄。
* 播放 TestTone/Test1KHz.wav 三次。
* 不再有任何動作

代替按 "+"，您也可以按 "-" 以以下順序啟動這些測試：
* "Start test of UDISK file" ("Cashe toshe upau in dje") 接著是 "Test of UDISK file passed" ("jon de toshe dchin tao") 或 "Test of UDISK file failed" ("jon de toshe she by")
* 循環播放 "if you want to hear the manual for that game tip on the info sign on the game plan"（非中文，而是點讀筆語言）。有時您可以按 "+" 離開此模式，點讀筆會跳至 "+" 區段描述的其中一個測試。

在測試模式中，您無法變更音量或停止測試樣本播放。

USB 儲存開機模式 (韌體快閃)

請另見 Hardware Details 區段！

此模式（已確認！）允許使用 Anyka Burn Tool 寫入新韌體。

若在啟動期間將 GPIO13 連接到接地，即可啟動此模式。這可透過 1 kOhm 電阻連接標記區域的焊墊輕鬆完成。直接連接可能也有效，但可能損壞點讀筆。

由於 PCB 上的這兩個焊墊與電池艙中的兩個小孔對齊，甚至無需打開點讀筆即可進入 USB 儲存開機模式。缺點：舊版點讀筆有一層箔保護兩個焊墊免受外部存取。輕微修改此箔，應可透過兩個孔存取。對於 B6 版 (4 GB)，此變通方式不必要，因為箔在正確位置有切口。

點讀筆在 USB 儲存開機模式下有 USB PID 038D 和 VID 04D6，電腦會這樣辨識：

(技術細節：字串 "Snowbird2_Massboot>" 和某些其他位元組在啟動後立即以 38400 bps 的 UART 協定透過 GPIO13 發送)

逐步步驟（方法 1，已在 B6 型號測試）：
1. 移除電池並等待 10 秒（確保點讀筆處於已定義狀態）。
2. 插入電池但勿按開機按鈕。
3. 啟動 Burntool.exe (v3.0.18) 並匯入 .upd 檔案（例如：若點讀筆有 Micron Technologies 快閃記憶體，則為 Update3202MT_fr.upd；若有其他供應商快閃記憶體，則為 Update3202_fr.upd）。
4. 使用 ~1 kOhm 電阻橋接 GPIO13 和 GND
5. 在電阻仍就位時按住並保持開機按鈕。現在點讀筆應處於 USB 儲存開機模式，您可以移除電阻。若正確執行，您不會聽到提示音（因為 TT 未從快閃記憶體執行 TT 軟體）。
6. 透過 USB 將點讀筆連接到 PC，並全程保持按住開機按鈕（否則點讀筆會再次關機）。
6. Burntool 偵測到點讀筆準備就緒，並在短時間後自動啟動快閃程序。
7. 達到 100% 標記後（約 30 秒至 2 分鐘之間），您可以釋放開機按鈕並從 USB 斷開點讀筆。

重新啟動點讀筆後，您應有一支如新且可用的點讀筆。

逐步步驟（方法 2，適用於 B5 型號，也許方法 1 也適用）：
1. 移除電池
2. 插入電池
3. 透過 USB 將點讀筆連接到 PC
4. 使用 ~1 kOhm (820 Ohm 也可) 電阻橋接 GPIO13 和 GND
5. 按開機按鈕並在約 2 秒後移除電阻。現在點讀筆應處於 USB 大容量儲存模式，且 PC 會公告發現新裝置

基於 ZC3201 的裝置，此程序無效。這些點讀筆在透過 USB 連接時會自動啟動（即使無電池！）。進入儲存開機模式的方式應為此（不涉及開機按鈕）：

逐步步驟（方法 3，適用於 A4 型號）
1. 插入電池
2. 開啟 Tiptoi
3. 關閉 Tiptoi
4. 等待 ~10s
5. 透過 USB 將點讀筆連接到 PC
6. 使用 ~1 kOhm (820 Ohm 也可) 電阻橋接 GPIO13 和 GND

可透過重新啟動點讀筆離開 USB 儲存開機模式。

則存在本貢獻未涵蓋的其他故障。


帶連接器的攝影機板

此例中，pin 2 (J1) 的接觸區與 CMOS 板分離，因此至附近通孔接觸斷開。此通孔接觸將 SDA 訊號傳至 CMOS 板另一側正對的 CMOS 晶片。因通孔位於 J1 和 J3 之間轉接板下，无法直接焊接 pin 至通孔。因此需完全將轉接板從 CMOS 板脫焊，以存取 SDA 通孔殘餘部分。最佳方式使用熱風焊接設備。
分離轉接板後，可將細銅線焊接至 SDA 通孔殘餘。線長應足夠置於 pin 1 (J1) 外側，以供後續焊接至 pin 2 (J1)。若線太短，可能無法最終保持至通孔的連接。準備好額外銅線後，可將轉接板的 7 個 pin (除 pin 2 (J1)) 焊接至 CMOS 板。最後將銅線開放端焊接至轉接板的 pin 2 (J1)。如前所述，若 pin 2 (J1) 與其他任一 7 個 pin 可測電阻，即連接建立。

OID

光學識別碼 (OID) 是 Tip-Toi 用來將數字編碼成黑色方塊圖案的方法。這些圖案隨後印在 Tip-Toi 產品的表面上，由點讀筆讀取並解碼，用作執行中腳本的輸入。儘管肉眼可見，此碼僅輕微干擾印刷內容。

(圖片 "Codierung im digitalen Papier (Detail einer Spielkarte)" by Schwesterschlumpf CC-BY-SA 3.0)

OID 編碼於一個 16 個像素的圖案中，橫跨 1 mm x 1 mm 的正方形。像素（每個 0,05 mm x 0,05 mm）第一列和第一行的像素用來定義網格。由於第一列第三個像素有輕微凹陷，因此可確定圖案的方向。

其餘像素 並未 對齊由其他像素定義的 4x4 網格。相反，其餘像素的四進位值由空間偏差定義：從右下（0）經左下（1）、左上（2）到右上（3）：

這 9 個像素中，左上像素作為校驗碼/奇偶位元。其餘像素依列從左上（最高有效位元）讀取至右下（最低有效位元）。此 GitHub 儲存庫中有一個 HTML/JS-OID-Decoder，可互動式展示解碼過程。注意：整數的原始值使用對映表/偏移量進行混淆。

這是逆向工程的結果（即長時間盯著十六進位碼），可能並不總是準確。此外，它也不完整；請參閱 README.md 中的待辦事項清單。

檔案格式也在 GME-Format.md 中有描述。不幸的是，那裡的資訊傾向於與這裡維護的資訊有所出入。

檔案格式由這些部分組成
* 一[[header|GME Header]]，包含偏移量指向
* 資料區域，其中包括 [[play scripts|GME Play script]]、[[games|GME Games]]、[[audio files|GME Media file table]] 和其他內容，最後是
* 一[[checksum|GME Checksum]]。

所有數值皆以 little-endian 格式儲存；本文檔中的偏移量為十六進位數字，以慣用（big-endian）格式印出。因此，如果在十六進位傾印中看到 d5b2 0100，那就是指向位置 0x1B2D5 的偏移量。

GME Header

長度：512 位元組

標頭以這 8 個 32 位元數字開始，並列出其偏移量：
* 0x0000: 32bit offset to the [[play script table|GME Script table]]
* 0x0004: 32bit offset to the [[media file table|GME Media file table]]
* 0x0008: 32bit。若在可運行的遊戲檔案中更改此值，將不再被接受。其值為所有目前見過的 tiptoi 產品皆為 0x0000238b。可能是 Chomptech 的 Ravensburger 客戶編號。
* 0x000C: 32bit。到一個 [[additional script table|GME Additional script table]] 的偏移量。用途未知。
* 0x0010: 32bit。到 [[game table|GME Game Table]] 的偏移量
* 0x0014: 32bit。產品 ID 碼 (== 第 1 頁開機符號的 OID 碼)
* 0x0018: 32bit。指向暫存器初始化值的指標 (16bit 計數器後接 n×16bit 值。第一個值為暫存器 $0，接著 $1 等等。)
* 0x001C: 原始 XOR 值 (8bit)，見 [[media file table|GME Media file table]] 說明。
* 0x001D: 三個位元組，意義未知，目前所有見過的產品皆為 0。
* 0x0020: 一個 可變長度 字串，由其長度 (8bit) 及該長度的字元組成。新發現顯示字串必須由 48 或 49 位元組組成 (至少對非德文點讀筆而言)。常見為 CHOMPTECH DATA FORMAT CopyRight 2009 Ver2.xx.yyyy (產品間有所不同，xx 也可能僅一位數)。
* 接著是 8 位數字日期字串 (20111024)。日期字串似乎為可選，但有一條件：若後接語言字串，則日期必須至少包含一個 ASCII 數字。
* 接著是可選語言字串。目前已知：GERMAN、DUTCH、FRENCH、ITALIA、RUSSIA、ENGLISH。若提供語言字串，則必須符合點讀筆上運行的韌體語言 (不清楚檢查位置；檔案 .tiptoi.log 在此不被考慮！)，否則點讀筆將忽略它。若缺少語言，任何 TipToi 點讀筆皆會接受該檔案。點讀筆讀取語言字串不超過 6 個字元。
* 接著是一連串零直到位置 0x5f 包含在內。
* 0x0060: 到一個 [[additional media file table|GME media file table]] 的 32bit 偏移量
* 0x0071: 到 [[playlistlist|GME Playlistlist]] 的 32bit 偏移量，用於開機聲音 (當辨識產品時播放。若為 0，則不播放聲音。)

以下條目可能僅從 Version 2.10.0901 起存在：
* 0x008C: 到 32bit 值表格的 32bit 偏移量，看似特殊 [[media flag table|GME media flag table]]？有些產品在此為 0。
* 0x0090: 到 [[game binaries table|GME Game binaries table]] 的 32bit 偏移量 (可能是 ZC3201 的遊戲)
* 0x0094: 到 [[special symbols|GME Special symbols]] 的 32bit 偏移量
* 0x0098: 到另一個 [[game binaries table|GME Game binaries table]] 的 32bit 偏移量 (可能是 ZC3202N 的遊戲)
* 0x009C: 32bit。用途未知，總為 0。
* 0x00A0: 到另一個單一 binary 的 [[game binaries table|GME Game binaries table]] 的 32bit 偏移量 (可能是 ZC3201 的主 binary)
* 0x00A4: 32bit 旗標。可為 0 或 1。
值 0：標頭其餘部分填滿 0。
值 1：標頭包含以下一個或多個偏移量。
* 0x00A8: 到另一個單一 binary 的 [[game binaries table|GME Game binaries table]] 的 32bit 偏移量 (可能是 ZC3202N 的主 binary)
* 0x00C8: 到另一個單一 binary 的 [[game binaries table|GME Game binaries table]] 的 32bit 偏移量 (可能是 ZC3203L 的主 binary)
* 0x00CC: 到另一個 [[game binaries table|GME Game binaries table]] 的 32bit 偏移量 (可能是 ZC3203L 的遊戲)
* 接著是一連串零直到位置 0x01FF 包含在內。

GME Media file table

媒體檔案表格由偏移量和長度（兩者皆為 32 位元組）的配對組成。
此清單中記錄數似乎沒有明確定義，因此我們會持續檢查直到
* 清單中第一個參照的媒體內容開始，
* 或出現 [[additional media file table|GME media file table]]，其後接著第一個
媒體內容。

媒體檔案本身使用簡單的加密方案，採用神奇 XOR 值 (x)：
- 值 0x00、0xFF、x 和 x XOR 0xFF 保持不變
- 其他所有值則逐位元組以 x 進行 XOR 運算。

神奇 XOR 值可透過找出使第一個媒體檔案的前 4 位元組讀取為 OggS 或 RIFF 的數字來取得。

在位置 0x001c 的標頭中，有韌體用來推算真實 XOR 值的原始 XOR 值。它可能使用某種演算法或查詢表。目前觀察到的所有 TipToi gme 檔案在此處的相同原始 XOR 值會導向相同的真實 XOR 值。截至目前，已透過檢查現有 gme 檔案識別出約 55 種不同的組合。

[[additional media file table|GME media file table]] 的用途不明。對許多檔案而言，它與主要音訊表格相同，對某些檔案僅單一檔案不同。

也許 [[media flag table|GME media flag table]] 只適用於這兩個表格之一。

GME Media flag table

  • 它緊接在暫存器初始化值之後。
  • 僅見於包含二進位檔案的 GME 檔案中。

  • 用途未知。

GME Play script

一個播放腳本由一個 16 位元數字（定義後續清單的長度）和一個 32 位元偏移量清單所組成。這些偏移量指向 [[script lines|GME Script line]]。

GME Playlist

播放清單由一個 16 位元數字（定義後續清單的長度）以及一個指向 [[media file table|GME Media file table]] 的 16 位元索引清單所組成。由於「隨機播放」指令僅認識用於範圍定義的 8 位元值，因此播放清單的大小可能限制為 256 個索引。

GME Playlistlist

一個參照 [[playlists|GME Playlist]] 的清單。一個 16 位元值，後跟該數量的 32 位元偏移量指向播放清單。

GME Register init values

這是一個 16 位元值，用來定義產品中使用的暫存器數量，後面接著該數量的 16 位元值。第一個值是暫存器 $0 的初始值，接著是 $1 等等
暫存器可以存放 16 位元值，並在播放腳本中被引用。

GME Script line

一行腳本由一組條件式、一組動作，以及所謂的[[playlist|GME Playlist]]組成，該播放清單包含[[media file table|GME Media file table]]索引。

一行腳本的格式為 aaaa conditionals... bbbb actions... cccc media...，其中
* a (uint16) 是條件式的數量。每個條件式由 8 個位元組組成。
* b (uint16) 是動作的數量。每個動作為 7 個位元組。
* c (uint16) 是一個播放清單

條件式

條件式的格式為 t1 aaaa cccc t2 bbbb
* t1 & t2 (uint8) 分別為 a 和 b 的類型 (0 == register, 1 == value)
* a & b (uint16) 暫存器的值或 ID
* c (uint16) 是比較運算子
只有當暫存器與值或其他暫存器的比較成立時，才會考慮該行的其餘部分。

比較運算子

已知的比較運算子有：
* FFF9 (在 tttool 的輸出和 yaml 檔案中寫為 $r==m?)：等於
* FFFA (在 tttool 的輸出中寫為 $r>m?)：大於
* FFFB (在 tttool 的輸出中寫為 $r<m?)：小於
* FFFD (在 tttool 的輸出中寫為 $r>=m?)：大於或等於
* FFFE (在 tttool 的輸出中寫為 $r<=?)：小於或等於
* FFFF (在 tttool 的輸出中寫為 $r!=m?)：不等於

動作

動作的格式為 rrrr cccc tt mmmm
* r (uint16) 暫存器的 ID
* c (uint16) 是指令
* t (uint8) m 的類型 (0 == register, 1 == value)
* m (uint16) 值或暫存器的 ID

指令

已知的指令有：
* FFF0 (寫為 $r+=m)：遞增 暫存器 $r 加上 m 或 $m 的值
* FFF1 (寫為 $r-=m)：遞減 暫存器 $r 減去 m 或 $m 的值
* FFF2 (寫為 $r*=m)：乘法 暫存器 $r 乘以 m 或 $m 的值
* FFF3 (寫為 $r%=m)：將暫存器 $r 設為 $r 模 m
* FFF4 (寫為 $r/=m)：將暫存器 $r 設為 $r 除 m
* FFF5 (寫為 $r&=m)：位元 AND 到暫存器 $r 加上 m 的值
* FFF6 (寫為 $r|=m)：位元 OR 到暫存器 $r 加上 m 的值
* FFF7 (寫為 $r^=m)：位元 XOR 到暫存器 $r 加上 m 的值
* FFF8 (寫為 Neg($r))：取反 暫存器 $r。
* FFF9 (寫為 $r:=m)：設定 暫存器 $r 為 m 或 $m 的值
* FFE0 (寫為 P*()：播放一個 媒體清單中的隨機樣本
* FFE1 (寫為 PA*()：播放所有 媒體清單中的樣本
* FFE8 (寫為 P(m))：播放 索引清單中第 m 個條目的音訊。
* FB00 (寫為 PA(b-a))：播放所有 該包容範圍內的樣本。a := lowbyte(m), b := highbyte(m)
* FC00 (寫為 P(b-a))：播放一個 該包容範圍內的隨機樣本。a := lowbyte(m), b := highbyte(m)
* FD00 (寫為 G(m))：開始遊戲 m。
* F8FF (寫為 J(m))：跳轉 到腳本 m。
* FAFF (寫為 C)：取消遊戲 模式。
* FF00 (寫為 T($register,123))：計時器動作。

目前未知的指令有 FE00 和 FF00 (理論上可能還有更多，但這些已在實際使用中出現)。FE00 似乎與計時器和隨機數有關。

指令 P、G、J 和 C 似乎會忽略它們的暫存器，C 也忽略其參數 (總是 FFFF)。

GME Script table

在 0x0000（通常為 0x0200）所引用的位置，是腳本表格。它由以下組成：
* 32 位元組：最後使用的 OID 代碼
* 32 位元組：第一個使用的 OID 代碼
* 接著是 32 位元組偏移量，指向 [[play scripts|GME Play script]]。這些偏移量與 OID 代碼線性對應。
例如 WWW_Bauernhof：第 6 頁的第一隻小豬有 OID 代碼 1499，對應的播放腳本位於 0x766A。腳本表格中的第 100 個 32 位元組單詞包含該偏移量。因此 4×(OID - 1401) = 腳本表格索引 + 8。此範例中的值 1401 是產品中第一個使用的 OID 代碼（腳本表格中的第二個 32 位元組單詞）。
* 這些偏移量中的某些為 0xFFFFFFFF。這表示對應的 OID 代碼在產品中未被使用。
* 偏移量的結尾可於 (腳本表格 + 8 + 4×(最後使用的 OID 代碼 - 第一個使用的 OID 代碼)) 找到。

加密

顯然，音訊檔案與點讀筆綁定。這似乎是透過為每個點讀筆個別建立的獨立 keyfile 來實現。RAV 檔案本身很可能使用通用金鑰加密，而點讀筆透過解密 keyfile 取得該金鑰。
另請參閱 ubuntu wiki 的 tiptoi 條目。

Keyfiles

Keyfiles 很可能包含解密 RAV 檔案所需的金鑰。每次下載的 keyfile 內容完全不同（即使輸入相同的點讀筆序號），這暗示使用鹽值清單或其他類似加密技術。此外，金鑰也以某種方式使用了您下載時需輸入的點讀筆序號。

只要 RAV 檔案尚未與點讀筆連結，就只能下載空的 keyfile。

檔案格式

RAV 檔案一律以 "Ravensburgerv03" 開頭，後接一個空字節。此字串在舊款點讀筆的韌體中找不到。觀察後續位元組的統計資料，它們似乎分佈相當均勻（暗示強加密方法）。僅 0x00 和 0xFF 的出現頻率略高於平均值。這表示這些位元組可能會被使用的 XOR 變體略為不同處理。

REC file format

這頁旨在收集有關 *.rec 檔案的資訊，這些檔案是由 2018 年 TipToi 點讀筆在內建麥克風錄音時建立的。

這些檔案的命名似乎使用以下結構（相對於 TipToi 點讀筆根目錄）：

./‹productId›book/RecSlot‹slotNumber›.rec

在此結構中，‹productId› 是用來錄製該檔案的「產品」（書籍/遊戲/…）的 ID。

‹slotNumber› 是一個 4 位數字，用來區分同一產品中的錄音。似乎一個槽位編號可以分配給任意 OID。通常有一個 OID 總是錄製特定槽位，另一個 OID 則播放該槽位。在 Ravensburger 書籍中找到的最低槽位編號是 0001（見範例）。

範例

  • "Die verrückte Weltreise"
  • ./129book/RecSlot0001.rec（第一頁的巫師，由 OID 3218 錄製，由 OID 3219 播放）
  • ./129book/RecSlot0007.rec（第二頁戴耳形服裝的男子，由 OID 3248 錄製，由 OID 3249 播放）
  • ./129book/RecSlot0003.rec（第一頁的鳥，由 OID 3226 錄製，由 OID 3227 以較高音調播放三次）
  • ./129book/RecSlot0013.rec（第二頁的小丑，由 OID 3286 錄製，由 3287 播放後接小丑笑聲）

檔案格式

這些檔案是與位元組 0x6a 進行 XOR 運算的 WAV 檔案。更具體來說，WAV 檔案使用 PCM（有符號、little-endian）編碼，採樣率 16 kHz（例外：在 "Die verrückte Weltreise" 中，藍色鳥的錄音採樣率為 8 kHz，可能與高音播放有關），16 位元樣本大小，單聲道。

Languages

Tiptoi 在不同語言版本

Tiptoi 點讀筆針對不同語言販售。每支點讀筆僅能處理與其語言相符的 GME 檔案。若不修改，無法在一支點讀筆上混用不同語言的 GME 檔案。

您也可以透過一些繁瑣的程序來切換點讀筆的語言。也有官方方法，但並非所有點讀筆型號皆適用。

修改 GME 語言

切換 GME 檔案語言有幾種可能性：
1. 使用語言變更功能，例如 tttool set-language FRENCH WWW_Bauernhof.gme 將語言設為 FRENCH。已知語言代碼有 GERMAN、DUTCH、FRENCH、ITALIA、RUSSIA、ENGLISH。
若要一次變更 Tiptoi 上所有 .gme 檔案的語言，Mac OS 使用者可在 bash shell 中執行以下程式碼 for file in /Volumes/tiptoi/*.gme; do tttool set-language GERMAN $file; done。將 GERMAN 替換為所需的語言代碼。
2. 使用十六進位編輯器變更語言特定部分。語言定義的位置與特性可參考此處：https://github.com/entropia/tip-toi-reveng/wiki/GME-Header
3. 使用 tttool 反組譯 GME 檔案，在產生的 yaml 檔案中變更語言，然後重新組譯 GME 檔案。此方法會遺失所有遊戲。
4. 使用 ttbox

Printing

這裡您可以找到有關如何成功列印 OID 的資訊，以及硬體相容性清單。

提示與技巧

  • 如果可能，請以 1200dpi 列印，有時 600dpi 似乎也能運作
  • 調整品質設定、解析度、對比度（特別是圖形/影像/文字品質最佳化設定可能有很大影響）
  • 使用不同紙張
  • 試試黑白列印與彩色列印
  • 試著提亮您的圖片
  • 確保列印時不重新縮放影像（即以 100% 比例列印）。
  • 測試問題是出在 tttool 產生的 OID 影像處理還是印表機本身的好起點，是列印 Ravensburger 的測試 PDF (法文版)。如果測試 PDF 在任何列印驅動程式設定的組合下都無法運作，很可能您的印表機無法處理 OID 碼的精細圖案。
  • 避免 OID 下方有太多結構
  • 分兩次列印背景與 OID，先列印背景，再列印 OID
  • 在您的 OID 圖形中試著使用更大的點
  • 避免任何縮放
  • 試著將 OID 點大小加倍用於 600dpi。這可以透過指定 tttool --dpi 600 oid-code 或 tttool --dpi 1200 oid-code 來達成。或者（例如針對現有的 PNG 檔案），您可以使用這個小型 shell 腳本來使用 ImageMagick 達成此目的（由 Sven Scholz 提供）（儲存為 double-oid.sh）。這會疊加 3 層額外的 OID，每層各偏移一個像素（一層向右、一層向下，以及一層向下+向右）：

#!/bin/bash
# Usage: ./double-oid.sh oid-<nn>.png
# -> produces oid-<nn>-composite.png
while [ $# -gt 0 ];do
   FILE=$1
   OUTPUT=${FILE%.*}"-composite.png"
   echo $FILE: $OUTPUT
   convert $FILE $FILE -geometry +1+0 -composite $FILE -geometry +1+1 \
      -composite $FILE -geometry +0+1 -composite $OUTPUT
   shift
 done
  • 列印基於 SVG 的 OID 時，試試不同的瀏覽器與應用程式。Firefox 似乎運作良好。

Ideas

在本頁面上，我們收集了有關此專案的各種想法。

書籍與應用程式的想法

  • 在「眼睛」圖示上點讀三次，會觸發額外的圖層。這會從宣布孩子發現了「秘密模式」（孩子們很喜歡這個！）開始，並允許播放兒歌，直到再次點讀「眼睛」圖示。
  • 使用 Tiptoi 技術製作相片書。
  • 製作自己的動物 (done)
  • 製作計算器應用程式 (done)
  • 擴充計算器應用程式，用作低階「條碼」收銀機，例如用於小型跳蚤市場的中央結帳
  • 將孩子們的名字整合到現有書籍中（個人化）
  • 使用 Tiptoi 為視覺障礙者和盲人服務 (example)
  • 實作互動尋寶遊戲
  • 透過音訊線纜將 Tiptoi 連接至 PC，以觸發 PC 上的動作（開啟網站、控制 Tiptoi 模擬器等）

tttool 的想法

  • 新增一個指令，將除錯輸出整合到現有的 .gme 檔案中。這可以透過在起始圖示上點讀 5 次來觸發。
  • 壓縮 gme 檔案，移除不必要的內容（例如重複的音訊表格）並對取樣進行降頻。這對使用第一代儲存空間有限的 Tiptoi 的使用者來說，將是一個實用的功能。
  • 整合一個功能，用來建立僅包含現有 .gme 檔案修改部分的檔案（delta gme）。這將允許在不違反版權的情況下，提供商業產品的修改版本。

硬體修改 的想法

  • 修改電池電量辨識功能，使其也能與可充電電池（特別是 Eneloop）相容。目前使用這些電池時，點讀筆會過早關機。
  • 啟用除錯模式（有一種中文除錯模式：啟動點讀筆時按住音量減鍵，然後按音量加鍵，即可聽到中文 OID 碼）
